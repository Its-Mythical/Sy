01

SY in four ideas

Strip the presentation away and SY is four ideas plus one boundary. Everything else in this document — the axes, the lanes, the edges, the mechanisms — is how those four are chosen, presented, and made to hold.

01

A strict, immutable core

Strictness is not incidental — it is what makes references point backward and pure data acyclic.

02

One effect mechanism

Row-polymorphic effects and handlers absorb I/O, mutation, errors and concurrency.

03

One memory model

Perceus exact reference counting, with scoped regions for the cycles strictness cannot exclude.

04

One foreign boundary

FFI at the edge, and nowhere else. Everything inside stays coherent.

And one uniform core

All four rest on a single small AST — seven forms: Var · Lit · Lam · App · Let · Case · Handle. Every surface form lowers to these, and every mechanism operates on them.

What is deliberately not a form

Constructors are first-class values — Cons(1, Nil) is App(App(Var Cons, Lit 1), Var Nil). Performing an effect is an App. if, match, while, for, do are all Case and Let. Type and effect abstraction are parameters on Lam and App. That uniformity is what makes Axis 1 (surface) and Axis 6 (macros) cheap — every surface construct is a macro over these seven.

The five-form floor

Fold Lit into nullary constructors and reduce Let to Lam applied to its argument, and you reach the theoretical minimum of five. But both earn their keep: Let is the only place let-generalization happens — kill it and HM inference breaks — and Lit is how unboxed primitives avoid the heap. Seven is the honest count; five is the floor.

04

The paradox we have to beat

Every great language is great partly for what it refuses to do. So "take the best of all of them" sounds like it should produce the ultimate language — and instead it produces PL/I. The features are not a menu; they are entangled, and the whole has a coherence the parts don't.

The kitchen-sink failure

Adding Haskell's type inference and Python's dynamic ease and C's machine closeness doesn't give you the union of their strengths — it gives you the union of their costs, plus a coherence problem. The design has to resolve the tension, not ignore it.

A boundary we accept, stated up front

SY is a strict language. That excludes laziness — a genuinely great idea from Haskell — so SY is not literally "the best of every language" but the best of the strict ones. This is a deliberate line, not an oversight: strictness is exactly what makes the DAG memory guarantee hold (§08). Naming the boundary is part of the design, not a footnote to it.

05

The surface: defaults and escape hatches

The two lanes are not architecture — they are ergonomics: a safe default plus an opt-in escape hatch at every axis. That is a normal design fact (every language has advanced features you choose), stated plainly instead of dressed up as a structure. The escape hatches are real; the framing is now honest about what they are.

Default lane

The curated best practice at this axis. Safe, readable, inferred, immutable, structured. A beginner writes the right thing by accident. This is the museum's curation.

Control lane

The proven full-power option at this axis. Explicit, owned, unscoped, raw. Opt-in, locally scoped, never silently changes the guarantees of the code around it. This is the workshop's reach.

The everyday lane on the left; the same constructs pushed to the metal on the right. You move between them deliberately, never by accident.

default lane · everyday code
# types inferred · values immutable · concurrency structured
fn average(xs) =
  sum(xs) / count(xs)

data Shape = Circle(radius: Float) | Rect(w: Float, h: Float)

fn area(s: Shape) = match s
  Circle(r) -> pi * r * r
  Rect(w, h) -> w * h

# tasks cannot outlive their scope — no orphan threads
fn fetch_all(urls) = scope
  urls |> map(fn u -> async fetch(u)) |> join
control lane · when you mean it
# same language — opt in when you need the metal

# explicit ownership: zero-cost, deterministic
fn consume(own buf: Buffer) -> Report = ...

# escape structured concurrency, deliberately
@unscoped spawn background_worker()

# run any function at compile time to generate code
comptime fn accessors(fields) =
  fields |> map(fn f -> "fn get_" <> f <> "() = self." <> f)

# raw memory, arenas, pointers when you want them
unsafe:
  let p = alloc<Int>(4096)

The seven axes

These seven are not SY's architecture — they are the checklist the method works through. Every language must decide each axis; SY's answers are below.

AxisBest of historyDefaultControl
0 · Extensibilitythe meta-axis Racket #lang, Forth A small orthogonal core you can grow. A file can declare itself a new language.
1 · Syntaxhow you write it Lisp homoiconicity, Python readability Readable, low-noise surface syntax. Uniform core form (S-expr / AST) always reachable.
2 · Typeswhat's checked ML / Haskell inference Infer everything, check statically, no annotations. dyn escape, gradual refinements (comptime, not SMT).
3 · Memorywho frees it Rust ownership, Lisp/Java/Go GC, C manual Automatic: exact reference counting — pure data is acyclic by construction. A cycle collector guards only the FFI boundary. Ownership/borrowing, raw pointers, arenas.
4 · Concurrencymany at once Erlang actors, Go goroutines + channels Structured concurrency — scoped, joined, no orphans. Carried as an effect in the spine. Actors, channels, deliberate unscoped spawn.
5 · Paradigmhow you think Haskell FP, C imperative, Smalltalk OO, Prolog logic, APL arrays Functional core inside an imperative shell — the core is sealed by inferred effects. Logic sub-language, array/vector notation.
6 · Metaprogrammingcode that makes code Lisp macros, Zig comptime, reflection Hygienic macros over the uniform core. Compile-time codegen, runtime reflection.

A note on the cut: these seven are a chosen set, not the whole of language design. A module system, error handling and effects are real axes too — error handling and concurrency are carried as effects in the spine (§11), and the two hardest edges are §08.

The edges: where the lanes meet

Stating "two lanes" is easy. The hard part is the edge — what happens when data crosses from one lane into the other. Two proposed bridges hold up; each still leaves an honest leftover.

Edge A · MemoryShrink it

If the default lane is already reference-counted, then own/borrowing isn't a second runtime — it's a static discipline over the same one. Perceus (from Koka) makes this concrete: the compiler tracks reference counts and, when the count is 1, reuses the buffer in place — which is what makes pure functional code fast instead of garbage-generating. The two lanes share one representation.

And the design closes most of the cycle hole on its own: in a strict, immutable core every value is fully built before it can be referenced, so references only point backward in construction order — a DAG by definition. Pure Default-lane data is therefore acyclic by construction, and Perceus is exact over it: no cycles to leak, no tracing needed.

What still needs care: the guarantee is bought by strictness, not immutability alone — allow any lazy binding and cycles reappear. Recursive and mutually-recursive closures are the one pure exception and must be compiled as static/grouped edges, not heap self-pointers. And the FFI boundary is the new edge: foreign or GC'd code can inject cycles, so the tracing collector isn't deleted — it's demoted to the boundary, where it belongs.

Edge B · TypesShrink it, honestly

Hindley–Milner really does break once you add ad-hoc overloading, higher-rank types, and array broadcasting. Bidirectional checking (a check mode and an infer mode) is the standard fix — and it wraps HM rather than replacing it: infer bottom-up to make unification constraints, push an expected type top-down to guide them. Crucially, check mode only switches on when you write a signature — so unannotated code stays in pure HM and pays no annotation tax.

The honest limits: higher-rank types and polymorphic recursion need signatures even in the default lane, because HM fundamentally cannot infer them. And refinements (tensor dimensions, index bounds) are made gradual rather than SMT-solved — self-hosted as comptime functions plus dimension unification: checked statically where the constraint is decidable, a single runtime check at the boundary where it isn't. That trades SMT-grade proof power for determinism and coherence — the right trade here, but a real one — and comptime refinement evaluation needs a termination budget, or a bad refinement can hang the compiler.

09

Every axis is an unavoidable decision

A language cannot leave any axis unanswered. A dynamically-typed language still has a type system — "one universal type, checked at runtime." A language with no macros has made a metaprogramming decision: none. Silence is still an answer.

Foundational

You cannot build the language at all without these — they're the substrate everything rests on: syntax & semantics, evaluation, memory lifetime. Cannot be retrofitted later without breaking everything.

Additive

The language works fine with the answer "none": an explicit concurrency model, metaprogramming, extensibility, error handling. Rust without macros is still Rust. Once the effect-spine exists (§11), several of these — concurrency, errors — are simply expressed as effects rather than built as separate subsystems.

Why this makes the two-lane design total

Because every axis is a decision, the design must hold a stance at every axis — even the ones it doesn't feature. The default lane is "the answer when you don't want to think about this axis"; the control lane is "the answer when you do." A axis with no stance is a axis decided by accident — exactly the failure we're avoiding.

10

The one rule that holds it together

Coherence before coverage

SY absorbs the best idea from each tradition only where it can sit inside one consistent default world. Everything else waits in the control lane. That single constraint is what separates a synthesis from a kitchen sink — and it means the design will always be able to say "not yet" to a good idea, which is exactly what the languages that survived did.

The honest caveat: a language is not adopted on merit. Python won because it was already there. Any new language competes on ecosystem and inertia long before it competes on design — so SY's real test would be whether the small core and the #lang layer let a community grow it faster than the incumbents can absorb the same ideas.

11

The effect-spine

The effect-spine is SY's engine. One mechanism — row-polymorphic effects and handlers — carries I/O, mutation, errors and concurrency, and it is what tells the compiler which functions are pure. That is what earns the memory guarantee, and why the spine is not a separate subsystem but the thing the whole design runs on.

The answer: infer it

The compiler infers each function's effect from what it actually does — the union of its callees' effects. No annotations in the default lane. The Default lane presents effect-free interfaces — empty residual rows — and the compiler enforces that those interfaces cannot leak effects outward, so the core is sealed by construction, not by convention. (A body may still use effects internally and handle them — see §12.)

The payoff: one mechanism

I/O, mutation, throwing errors, and concurrency are all just effects — one system instead of four. Error handling stops being an orphan; it's an effect like any other. This is Koka's model (row-polymorphic effect inference), the same lineage as the Perceus memory of Edge A.

Why this underwrites the memory guarantee

SY can only promise "pure values are DAGs, so RC is exact, so the tracing collector stays at the boundary" if the compiler can tell which functions are pure. Purity inference isn't decoration on top of the memory model — the memory model depends on it. That's Axis 5 and Axis 3 reinforcing each other: the cleanest instance of coherence in the whole design.

The cost, stated honestly

Inferred effects are harder to diagnose. When a function turns out impure, the cause is transitive — "effectful because of a call six axes down" — and clear messages for that are genuinely hard. So the recommendation is inference + optional explicit effect signatures at boundaries + heavy investment in diagnostics: infer by default, mark only when you want to pin a contract.

The division of labour

The two lanes are the interface; the effect-spine is the engine. The two lanes give the programmer a clean, annotation-light surface with an escape hatch at every axis; the spine gives the compiler one mechanism to power all of it. It was never a competing design — the spine is what makes SY's guarantees real rather than aspirational.

12

Local effect masking — and why it isn't a choke point

The pure core can't leak effects outward — but should it be able to use them internally? Yes: a function may mutate locally, throw internally, or run local concurrency, as long as a handler discharges those effects before it returns. The payoff isn't just speed — it's that effects are handled where they arise, so nothing funnels through a single place.

The rule, reframed

Purity means an empty residual effect row after all handlers are applied — not "no mutation happened." So the shell is a role, not a location: a function is shell exactly when its residual effects are non-empty, wherever it sits. "The core may not call the shell" becomes "the core may not leak effects outward" — it can freely use them inside.

Why it never becomes a choke point

Because handlers are local and composable, adding a new effectful algorithm never means routing it through main or threading state up the call chain. A new effect is a new row entry plus a handler — not a new subsystem. And the ambient boundary stays thin (only true I/O, time, and foreign calls), so it never accumulates into a bottleneck as the codebase grows.

One refinement to Edge A

Masking sharpens the memory guarantee rather than weakening it: the promise becomes "values that escape the pure world are DAGs" — not "all values everywhere are acyclic." But the tempting next step, "so temporary local cycles are fine because they're uniquely owned," is wrong — a cycle is exactly the refcount-≥-2 case. It needs a scoped arena, which is Invariant 1 in Section 13.

13

The invariants, and where they meet code

Putting the whole language on one engine and local masking is elegant — but it stands or falls on two compiler invariants. Skip either, and the guarantees quietly break under real-world pressure.

Invariant 1 · A local cycle is not "refcount 1"

The shortcut — "temporarily-cyclic local structures are fine because they're uniquely owned" — is wrong, and it's worth being blunt. A cycle is the refcount-≥-2 case: two local nodes pointing at each other each carry a count of at least one from the other. Drop the root and plain Perceus decrements 2 → 1 and leaks the cycle; return one of those nodes and the cycle escapes into the pure world, breaking the DAG guarantee outright.

The fix uses the tool Axis 3 already has: tie every mutable or cyclic scratchpad to a scoped arena with a phantom scope token — the same idea as Haskell's runST or Koka's scoped heap effect. The scratch lives in the handler's arena, which is bulk-freed the instant the handler discharges, and the type checker enforces that only immutable, acyclic Default-lane values can cross the return boundary. Cycles stay local by construction; nothing leaks and nothing escapes.

Invariant 2 · Not every handler is the same at runtime

If the engine carries local state, exceptions, concurrency, and nondeterminism through one mechanism, the compiler must not run them all through a general delimited-continuation handler — that would make sort orders of magnitude slower than C. Handlers have to be specialized by resumption discipline:

Resumption disciplineExamplesHow it compiles
Tail-resumptivelocal state, config readsinlined into raw register/stack ops + Perceus in-place updates
Single-shotinternal exceptions, structured concurrencystandard stack unwinding or a state machine
Multi-shotseeded nondeterminism, logic searchclone continuation frames — Control lane only

The design rule that falls out: the Default lane's local masking is restricted to tail-resumptive and single-shot effects, so everyday code compiles to something as fast as hand-written imperative. Multi-shot — the expensive one — is opt-in in the Control lane, where logic and nondeterminism live.

And the surface: implicit by default

Should sort need an explicit handler block to discharge its local state? No — that would re-create the annotation tax masking exists to remove. Instead, every function body is an implicit handler boundary for localizable effects: declare a local mutable variable, mutate it, and the compiler scopes and discharges it for you. Explicit handle blocks are reserved for custom effects, choosing a non-default handler, and multi-shot logic — the Control lane. It's the same principle as types: automatic by default, explicit when you want control.

surface syntax · implicit handler boundary
fn sort(xs: List) -> List =   # effect row: EMPTY — pure to the outside
  var a = xs.to_array()        # local state — scoped implicitly
  for i in 0..len(a):
    swap(a, i, min_index(a, i))   # raw in-place mutation, inlined
  return a.to_list()           # only an immutable value escapes

Where they meet everyday code

Both details below are the same underlying fact — uniqueness and scope are tracked in the type — seen from two angles.

Zero-copy freeze & thaw across the boundary

If to_array() and to_list() had to copy all N elements at entry and exit just to satisfy "only immutable values cross the boundary," local mutation would lose half its point. But when the caller hands in a uniquely-owned collection (refcount 1) whose element type is acyclic, the compiler can thaw the immutable buffer in place, mutate it inside the implicit handler, and freeze it back on return — zero copying. Perceus and masking pull the trick off together.

Two preconditions, not one: unique ownership (a shared input must copy or copy-on-write) and acyclicity — a type attribute, which is the very same "the compiler knows which types can form cycles" fact from Edge A, doing double duty. The scoped arena of Invariant 1 is only needed when local code builds pointer-rich mutable graph nodes that could actually close a loop.

Closures that capture local var state

A helper closure inside sort — items |> map(fn x -> count += 1; x * 2) — is performing the outer function's local state effect. That's safe as long as it runs inside the implicit handler: synchronously, or inside a Default-lane structured-concurrency scope guaranteed to join before sort returns.

It is unsafe the moment the closure is returned or handed to @unscoped spawn — the local var would outlive its handler. The phantom scope token from Invariant 1 catches this automatically: the closure's effect row carries the outer scope token, so the type checker statically rejects returning it or spawning it unscoped. No dangling stack references, by construction — the same trick as runST's rank-2 region.

The same fact, twice

Zero-copy reuse and escape-prevention look like different optimizations, but they are one idea: uniqueness and scope live in the type. Because the compiler can see both, it can hand you the speed of in-place mutation and the safety of no-escape at the same time — which is exactly what makes the pure core both fast and trustworthy.

Why it isn't a third expression lane, and the rules that keep it safe:

ConcernWhat the foreign boundary does
KindThe two lanes express SY semantics; the foreign boundary imports foreign semantics. It is the one place that sits outside the coherence rule — the deliberate hole.
EffectsEvery foreign call is an ambient effect — it cannot be masked. The spine tags it, so purity stays honest even when you call out.
TypesForeign values cross through an FFI type mapping and arrive as opaque handles. The mapping is lossy at the edges — Python's dynamic types and Rust's lifetimes don't survive the crossing intact.
MemoryForeign objects live under their own model; SY treats them as opaque handles — not DAGs, not refcounted by Perceus. The exact-RC guarantee stops at the boundary.
What it isA boundary, not a host: you call foreign code, you don't run foreign semantics natively. SY becomes a language with interop, not a polyglot runtime.

Two lanes for expression; one door for foreign semantics

The foreign boundary is not a way to write SY — it's a way to reach out of it. That distinction is why the design can add literal support without re-opening the kitchen-sink problem: the foreign semantics never leak into the coherent core; they stay quarantined at the edge.

The honest cost

Everything the design guarantees is bought inside SY — purity, exact RC, the DAG property, masking. At the foreign boundary, all of it stops. That's acceptable because it's the same FFI edge §08 already admitted never fully closes; naming it as a boundary just stops pretending otherwise. And it's practical: every serious language has foreign interop, so refusing it would cost SY more than it buys.

Open problems — what isn't solved yet

A design that cannot name its own gaps is selling, not designing. Here is what SY does not yet answer.

Adoption

The real risk isn't the design

Every other problem here is smaller than this one.

RiskA language is adopted on ecosystem and inertia, not merit. Incumbents will absorb the same good ideas into Python, Rust, or Swift long before SY reaches critical mass. The #lang layer is the only lever that might outrun that.
Diagnostics

Effect errors are transitive

The cost named in §11, still unsolved.

Gap"Impure because of a call six axes down" is hard to explain well. Handlers give a natural place to anchor messages, but good effect diagnostics remain an open, research-grade problem.
Performance

Handler specialization must actually deliver

Invariant 2 (§13), taken on faith until built.

GapThe whole "fast pure core" claim rests on tail-resumptive and single-shot handlers compiling to raw operations. If specialization falls short, the default lane is slower than C and masking loses its point.
Axis 1

The surface syntax is unspecified

The one axis a human actually touches.

GapIndentation rules, the surface grammar, and the surface-to-core desugaring table are not yet written. Until they are, SY is a semantics without a syntax.
Types

Is acyclicity inferred or annotated?

Freeze/thaw (§13) depends on it.

GapZero-copy thaw needs the compiler to know a type is acyclic. Whether that attribute is inferred, declared, or both is undecided — and it gates a key optimization.
Compiler

Implicit handlers must be verified

The flip side of "implicit by default" (§13).

GapIf every function body is an implicit handler boundary, the compiler must prove its local effects are tail-resumptive or single-shot. That obligation has to be discharged, not assumed.
Framing

Which principle is on top?

The coherence rule and the effect-spine are the same fact seen twice.

Gap§10 says coherence binds the design; §11 says the effect-spine is the engine. They should be stated once as a single principle — and the FFI boundary stays an edge that never fully closes.
Complexity

The core is small; the compiler is not

"Small core" can undersell the real cost.

GapSeven AST forms hide a compiler doing HM + bidirectional checking + row-polymorphic effect inference + Perceus + scoped arenas + comptime refinements + handler specialization. The difficulty is concentrated in the compiler, not the surface — and that should be said plainly.
Effects

Localizable vs ambient isn't always crisp

The masking line (§12) has grey areas.

GapLogging, caches and buffered output sit between the two — local enough to mask, ambient enough to matter. The design needs a principled rule for the middle, not just for the two ends.
Structure

Is "two lanes at every axis" too uniform?

Some axes may not have a real second option.

GapThe rule is elegant, but does syntax really need a control lane? Forcing symmetry where no genuine second choice exists can manufacture complexity. The uniform rule may have to yield to "two lanes where a real alternative exists."

Why this section exists

None of these sink the design — but a spec that reads cleanly and hides its soft spots is the most dangerous kind. The gaps above are the difference between a design that reads well and one that ships.
